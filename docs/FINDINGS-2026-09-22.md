## TL;DR

- The **April profile (`ZP11.260417.009`, patch `2026-05-05`) stopped working
  during 2026-09-22.** It produced three green in the morning and produces
  **nothing** by midnight — on a brand-new AVD, fresh identity, same kernel, same
  modules, no debloat. Google withdrew it; nothing local changed.
- The current canary profile reaches **`MEETS_DEVICE_INTEGRITY` only**. BASIC and
  STRONG were not reproducible by any local means tried.
- **Ten silent failures** were found and fixed in this repo. Every one of them
  logged success while doing nothing. See "Bugs" below.

## The controlled A/B (the result that matters)

One device, one identity (`4553827889938236479`), three consecutive cold boots:

| Profile | Verdict |
|---|---|
| `ZP11.260417.009` / `2026-05-05` (the morning's 3-green config) | BASIC ✗ DEVICE ✗ STRONG ✗ |
| `ZP11.260821.010` / `2026-09-05` (current canary) | BASIC ✗ **DEVICE ✓** STRONG ✗ |
| back to September | **DEVICE ✓** (reproducible) |

Two conclusions:

1. **Verdicts are not pinned to a device identity.** Three different answers from
   one `android_id` within ~20 minutes. Repeated tests on one device are valid;
   you do not need a fresh AVD per experiment.
2. **The April profile died on 2026-09-22.** It was equally 4.5 months old that
   morning when it was green. Age was not the mechanism — rotation was.

## Device identity: what does and does not rotate it

On the original AVD the check-in id `4067661520090240516` survived **all** of:

- `pm clear` of `com.google.android.gms`, `.gsf`, `com.android.vending`
- `rm -rf` of all three data directories
- removing the Google account and deleting `accounts_de.db` + `accounts_ce.db`
- changing `ro.serialno`
- repeated cold boots

It rotated only by **building a new AVD** (`4553827889938236479`). If you need a
clean identity, `scripts/new-avd.sh` is the only known way.

Note: a fresh identity produced the *same* verdict as the old one, so the old
device was never "burned" — that hypothesis was tested and disproved.

## Keybox

All 15 entries in specter's catalog were tested or accounted for: 14 tested,
1 (`@Xiaomi_Lei_Jun v4-fix`) rejected as `KEY_COMPROMISE`-revoked. **Every
unrevoked one gives the identical verdict.** Keybox choice does not move BASIC or
STRONG here. `scripts/check-keybox.sh` validates every certificate against

observed printing both "Keybox is revoked by Google" and "Keybox is not revoked"

## Bugs fixed (all failed silently, all logged success)

1. `01-avd-prop-spoof.sh` hardcoded the fingerprint/ID/patch and never read
   `profile.env` — **no profile change could ever take effect**, and the live
   props contradicted the bind-mounted `build.prop`.
2. `04-prop-sweep.sh` used sed `\|` alternation, a GNU extension toybox lacks.
   Its `init.svc.*` / `ro.boottime.*` loops matched nothing and logged
   "deleted 0" as success. ~30 emulator props leaked to any app, no root needed.
3. `add_open_redirect` takes **three** args (`<target> <redirect> <uid_scheme>`);
   the script passed two, so ksu_susfs printed usage and did nothing. All four
   `/proc` redirects never existed.
4. `add_sus_map` does not register at post-fs-data (zero kernel entries; post-boot
   calls register fine). Layer 4 was never applied. Now re-applied by
   `service.d/13-susfs-late.sh`, verified against `dmesg`.
5. The `/proc` bind mounts carry their source SELinux label, so
   `/proc/{cpuinfo,version,modules}` were labelled `adb_data_file` and **Google
   Play Services was denied reading `/proc/cpuinfo`** (`avc: denied ...
   scontext=u:r:gmscore_app`). Granted via `ksud sepolicy`.
6. `10-wlan0-virtwifi.sh` / `12-checkin.sh`: `settings`/`svc`/`cmd`/`am` pass
   their stdout fd to system_server over binder; pointed into `/data/adb` the
   append is denied and the call dies with "Failed transaction (2147483646)" —
   into the very log that could not be written. Wi-Fi never connected and
   check-in never fired.
7. `verify-integrity.sh` read the check-in id from the **stale** GSF path
   (empty on Android 14+), reporting "not checked in" on every device. Its
   `--trigger` also cleared a non-existent DroidGuard path, so the reset was a
   no-op.
8. `ro.serialno` = `EMULATOR36X4X10X0`, `ro.build.characteristics` = `emulator`,
   `ro.build.description` = `sdk_gphone64_arm64-...` — never spoofed by anything,
   readable by any app, and contradicting `ro.build.fingerprint`.
9. `device/avd-config/config.ini` had `skin.path` hardcoded to the original
   author's home directory, and `forceColdBoot=no` / `forceFastBoot=yes` —
   directly contradicting REPRODUCTION.md §6. Anyone following the repo verbatim
   got a fast-boot AVD that skips the boot scripts.
10. `avdmanager create` yields `PlayStore.enabled=no` even on a playstore system
    image. Play Integrity cannot work at all. `scripts/new-avd.sh` now writes
    config from the repo template.

Two scripts referenced by INTEGRITY_CHAIN.md — `08-partition-props.sh` and
`06-bootloader-safe.sh` — **have never existed** in git history or on any device.

## Gotchas worth remembering

- `adb emu kill` is a plug-pull and does **not** sync the guest filesystem.
  An `install-device-setup.sh` run followed immediately by `adb emu kill` is
  silently discarded. `sync` first.
- `start_avd.sh` defaults to `AVD=Pixel_9_Pro_XL`. Always pass `AVD=` explicitly
  or you will test the wrong device and not notice.
- The KSU-Next manager randomises its package name when hidden, so
  `pm list packages | grep ksu` finds nothing. Root for shell must be granted in
  its UI; it is not automatic.
- `INTERNAL_ERROR (-100)` from the checker right after `pm clear
  com.android.vending` just means Play Store has not re-provisioned yet. Wait.
